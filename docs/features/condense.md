# Condense：历史整理与原文恢复

Condense 将较长的工具历史整理为摘要、去重引用或归档预览。模型在后续请求中读取整理后的视图；原始参数和结果保存在会话归档中，可通过 `context_tree_query` 按需查询。

模型摘要属于有损视图，原文用于补充细节。改写历史也会重建请求前缀，因此实际收益取决于后续请求数量和缓存复用情况。

**自动历史整理与空闲整段压缩（OCC）的初始状态均为关闭。**

## 启用与配置

```text
/pruner settings
/pruner on
/pruner status
```

配置位于全局 `<agentDir>/metis-pi.toml` 的 `[contextPrune]`。`agentDir` 默认为 `~/.pi/agent`，也可通过 `PI_CODING_AGENT_DIR` 指定。`/pruner` 命令会直接保存设置；手工编辑文件后执行 `/reload`。

| 命令 | 作用 |
| --- | --- |
| `/pruner settings` | 修改摘要模型、触发方式和保护项。 |
| `/pruner on` / `off` | 开关本地历史整理；归档查询始终可用。 |
| `/pruner status` / `stats` | 查看当前设置、整理进度和摘要用量。 |
| `/pruner now` | 开启 Condense 后，立即处理 pending。 |
| `/pruner compact` | 整理所有具备有效摘要的闭合小 chain，忽略 `rollingWindow`。 |
| `/pruner help` | 查看全部子命令。 |

字段、默认值和单位见[配置参考](../../metis-pi-config.md#contextprunecondense--occ)。

## 三层分组

消息边界决定分组，token 数量用于后续的收益与费用评估。

| 单位 | 范围 |
| --- | --- |
| 小 batch | 一次主模型请求产生的工具调用及其结果。同一请求中的多个工具调用组成一批。 |
| 小 chain | 从一条完整可见的 assistant 文本回复开始，到下一条文本回复、用户输入或 Goal 续推之前。 |
| 大 chain | 从一次用户输入或 Goal 续推开始，到下一次用户输入或 Goal 续推之前。 |

例如：用户提出任务 → assistant 回复 A → 两轮工具调用 → assistant 回复 B → 一轮工具调用 → 下次用户输入。这段历史包含三个小 batch、两个小 chain 和一个大 chain。

文本边界来自完整消息中的非空 `text`，包括同时含文本和工具调用的消息。thinking、流式片段、工具输出和 Condense 派生消息归属于所在段。用户输入到第一条 assistant 文本之间的工具工作形成独立起始段，每个新边界开启下一段。

下一边界出现前，当前段保持开放。大任务中的已闭合段可以独立进入候选评估。闭合表示文本范围完整；随后一条成功的主模型响应确认其中的工具结果已被消费。失败、中断或截断的响应会继续保留原文。

`batchingMode="turn"` 保持请求批次独立；`"agent-message"` 合并同一小 chain 内的相邻批次。单次摘要最多包含 24 个工具调用，并按输入预算拆成多个 chunk；语义边界在各 chunk 间保持一致。

## 何时整理

`pruneOn="agent-message"` 在完整可见文本回复后评估，是默认模式。`"on-demand"` 同时支持手动 `/pruner now` 和工具轮次上的压力、增长或尾部积压触发。每次触发都会经过下述保护、收益和预算检查，再决定是否替换。

| 处理方式 | 生成方式 | 适用条件与结果 |
| --- | --- | --- |
| 精确去重 | 本地哈希 | 工具名和结果正文完全相同，且已有可恢复记录。每次执行保留独立的参数、状态和引用。 |
| 规则摘录（packing） | 本地规则 | 处理可识别的成功构建、测试等输出，保留首尾以及错误、警告和结果行。 |
| 工具结果摘要 | 摘要模型 | 归档完整、已消费且位于近期保护范围之外的旧结果，通过收益、预算和费用检查后生成摘要。 |
| 小 chain 整理 | 复用已有摘要 | 将闭合段的工具历史替换为已有摘要与恢复引用，保留边界文本。 |
| 大输出落盘（spill） | 本地归档 | 单个结果超过 `spillThreshold` 时保存原文，并在视图中留下预览和引用。默认门槛为 65,536 字符。 |

自动摘要、packing 和 chain 整理都要求结果已被模型消费，并应用共同的近期保护。spill 在捕获阶段按大结果规则生成预览和引用；“已归档”与“模型已消费完整结果”是两个独立状态。失败调用参数和图片数量由各自的设置管理。

### 付费摘要压力与预算

设模型窗口为 `W`，Pi 自动压缩的有效容量为 `T = W − reserveTokens`。默认付费摘要压力线为：

```text
min(0.7 × W, 300000, max(0, T − 16384))
```

`T` 有解析结果时纳入计算。自动付费摘要还要求有效的上下文用量。`summaryBudget.maxBudgetWindowTokens` 配置其中的 300,000，与近期原文保护量无关。

`autoBudgetThreshold=false` 仅控制自动付费摘要。手动整理、本地规则和 Pi 原生压缩继续使用各自入口。增长与尾部积压触发也要通过付费压力和收益检查。

剩余待摘要内容低于 `minBatchChars`（默认 5,000 字符）时保留原文；设为 0 后，各批次直接进入后续预算检查。

默认单次付费替换至少净省 `max(2048, 被替换结果的40%)` 个本地计数 tokens，完整摘要消息最多 6,144 个，恢复引用、预览和包装均计入。单次摘要的工具历史输入最多 65,536 字符，小窗口模型会进一步收紧。

预算空间不足、摘要为空、发生截断或替换后变大时，视图继续使用原文，pending 留待后续处理。本地计数采用归一化消息的 o200k 分词；provider 输出上限、用量报告和账单分别由对应系统提供。预算公式见[摘要预算参数](../../metis-pi-config.md#contextprunesummarybudget摘要预算)。

### 近期原文与 chain 选择

自动工具摘要和 chain 整理共同保护以下内容，取各项的并集：

- 最近 **32,768 个估算 tokens** 的原文尾部（`minRecentTokens`）。
- 最近 **4 轮有效工具工作**（`minWorkTurns`）。有效轮次要求成功的主请求和有效工具结果。
- 等待模型消费的结果、指定保护工具和路径，以及回读宽限内的内容。
- 开放小 chain 的完整原文。

默认 `rollingWindow=3` 最多参考三个近期闭合小 chain，并与开放组共用 `minRecentTokens` 预算。选择从近到远进行，以完整组为单位；下一组超出预算时结束选择。近期尾部和有效工作保护独立生效。

`rollingWindow=0` 关闭链数参考，其余保护保持不变。显式 `minRecentTokens=0` 取消原文最低量和引用组的 token 限额，工作轮次及其他保护继续生效。

手动 `now` 使用配置的引用窗口，`compact` 覆盖全部安全闭合组。两者都保留指定保护，并要求归档完整和实际缩小。

## 缓存与费用

自动工具摘要、packing 和 chain 整理共用累计费用状态与再次改写条件。

1. **局部收益。** 闭合且已消费、正文为 2,048–65,536 个估算 tokens 的独立请求片段或小 chain，按自身收益评估。这个区间用于选择经济计算档位；小 chain 始终按消息边界定义。更大的候选和共享组按整体收益评估。
2. **总成本预测。** 总输入取本地投影与 Pi 当前用量估计的较大值，净收益取两种本地计数的较小值。改写后的首个冷请求单独计费；后续两条路径每次都新增 2,000 tokens，目标缓存命中率为 98%，缓存量受上一请求长度约束。每次请求按各自输入量选择报价阶梯，压缩侧含摘要费后须严格更便宜。
3. **预测范围。** 普通 batch 聚合比较后续 3 次请求，自动大 chain 和共享机械整理比较 24 次，有界独立候选最多比较 32 次。这个数值描述费用预测范围；实际整理发生在当前检查点。摘要请求发起前按输入和输出上限预留费用，尚未收到 usage 的请求沿用预留值。
4. **发布后复核。** 首个请求回执按输入、缓存读取和写入用量校正冷请求的增量费用；超出预测的损失补入待偿余额，用量缺失时保留全冷重建预留。后续改写要求余额结清，并新增至少 `max(minGainTokens, 上次净收益/4)` 的有效工作 tokens。有缓存折扣的模型还要在冷请求之后连续完成 3 次成功主请求，每次实际缓存命中至少 90%。

普通历史按内容不变的模型消息前缀估计首轮复用，旧压缩块重新渲染后仍可计入。远端检查点使用最近一次已观测请求及其缓存回执：会话、模型路由、检查点、来源编辑、提示词和工具定义相符时，从实测缓存量中扣除整个受影响后缀的估算量，将剩余部分计入首轮缓存。当前投影在上次请求后已有变化时，按更早的变化位置扣除。缺少匹配证据时采用全冷预算，Pi 用量未知时等待有效回执。

请求依据仅借用最近一次模型输入的消息引用，发布或重置时释放。Pi 用量以最近 provider 回执和后续消息推算，涵盖本地投影以外的请求开销；首个改写后回执继续校正预测与实际缓存的差额。

有界候选的绝对收益底线为 `min(2048, chainCompression.minGainTokens)`，比例按候选自身计算。较大的 chain 候选及共享 chain 组使用默认 8,192 和总上下文 10% 的门槛。工具摘要先逐一满足局部摘要预算，再纳入共享费用状态。

上下文超过 **256,000** 个估算 tokens 后，有界独立候选的修改范围限定在最后 **192,000** 内的旧内容，近期保护规则保持一致。这两个数值用于候选筛选；模型窗口与压缩目标由各自设置决定。

预测基于固定增长和缓存条件，实际费用以 provider 的 usage 与账单为准。短任务可能在冷请求和摘要费用摊回之前结束。无缓存折扣的模型以费用和工作增长作为复核条件。

### 报价来源与刷新

报价按以下顺序解析：

1. Pi 已注册模型的价格及上下文阶梯。先精确匹配，再按受限正则匹配分隔符和日期别名。`mini`、`pro`、`flash` 等型号限定词参与匹配；同一模型的多个报价一致时才采用。
2. [models.dev](https://models.dev/) 的本地快照，包括可识别的上下文阶梯价。
3. 前两项均无报价时，使用**缓存输入∶普通输入 = 1∶10** 的相对成本估算。相对单位用于策略比较，账单金额以 provider 为准。

缓存位于 `<agentDir>/cache/metis-model-prices.json`。启动、切换模型和新用户任务时，Condense 检查 Pi 的 `models-store.json` 与 Metis 安装标记；来源变化会触发目录重读，并在需要时后台查询 models.dev。已有快照继续提供报价，首次查询期间的自动改写等待结果。

`pi update --models` 对模型目录的修改会触发下一次检查。Metis 安装或更新的 `postinstall` 会写入刷新标记，`pi update --extensions` 更新 Metis 后也会生效。其他时间沿用当前快照；查询失败时保留已有报价或回退到相对估算，同一来源版本只尝试一次。

## 临近 Pi 原生压缩时

Pi 自动压缩已启用且有效容量 `T` 可解析时，上下文达到 **90% × T** 后，后续新增改写交由 Pi 原生压缩接管。当前前缀保持稳定，Goal 继续运行，Pi 在自然增长达到容量线时执行压缩。

这个交接涵盖 pending 摘要、去重、参数整理、spill、chain 和主动 OCC。在途候选进入该区间后，发布阶段会保留原文；已发生的摘要费用照常入账。已发布的整理结果继续重验与恢复，手动 `now`、`compact` 也保持可用。

## 摘要模型与故障处理

`summarizerModel="default"` 跟随当前会话模型，也可指定已注册的 `provider/model-id`。故障切换按主摘要模型、`summarizerFallbackModels`、当前会话模型的顺序尝试，重复项使用首次出现的位置。

摘要模型和备用模型会接收该批工具参数与结果。跨 provider 配置时，应选择符合资料权限的模型。

认证、模型不可用、超时和 provider 故障使用备用链。空输出、截断或预算拒绝会结束当前候选并保留原文。成功的备用模型会被复用，10 分钟后可重试主摘要模型。

## 原文与分页恢复

归档位于会话旁的 `<sessionId>-blobs/`，备份、移动和清理会话时应一并处理。归档在显示截断之前捕获输出，并导入 Pi bash 的完整输出文件。可恢复范围以 `archiveComplete` 为准，上游缺失会明确标记。

`context_tree_query` 是延迟加载工具。通过 `tool_search` 获取参数后，可直接调用或在 codemode 中使用。省略选择器会先列出证据目录，取得引用后再读取内容：

| 参数 | 用法 |
| --- | --- |
| `toolCallIds` | 工具原 ID、`t12` 等短引用或 `b1` 等 chain 块引用；重复原 ID 返回各次已索引记录。 |
| `parentToolCallId` | 按父调用读取子调用归档，包括 codemode 界面预览省略的部分。 |
| `sourceEntryIds` | 读取当前分支上的历史消息、压缩或摘要条目，组件为 `output`。 |
| `component` | 默认 `output`；`arguments` 读取原始参数，支持 `toolCallIds` 或 `parentToolCallId`。 |
| `maxBytes` | 每页完整 JSON 的字节预算，含元数据和游标；2,048–32,768，默认 32,768。 |
| `cursor` | 使用上一页的 `nextCursor`，保持相同的选择器和 `component`。 |

`toolCallIds`、`parentToolCallId`、`sourceEntryIds` 三者任选其一。分页按 UTF-8 安全边界切分。游标校验会话、当前分支可见性、选择和内容版本；来源失效后从新的第一页开始。

`eof` 描述分页进度，`archiveComplete` 描述原始捕获完整性。缺归档、未结束和捕获不完整都会返回明确状态。查询结果反映归档时的内容；当前文件或运行中进程的状态需另行获取。

原文回读会开启 `recoveryGraceTurns` 保护，默认持续 3 个大任务边界，用户输入或 Goal 续推各计一次。

## 空闲整段压缩（OCC）

OCC 使用 Pi 的普通文字摘要，由 `enabled` 和 `opportunisticCompaction` 共同开启。它在回复结束、消息已交付且工具空闲时尝试；远端加密路径拥有请求时，由远端路径完成压缩。

Pi 自动压缩启用后，OCC 按有效容量 `T` 调度：60% 开始等待，72% 可就绪，低于 52% 退出等待，90% 起交给自然压缩。等待三轮工作后若尚未就绪，本地摘要可以恢复执行。每次用户或 Goal 请求最多进行一次 OCC 尝试。

本地改写发布、OCC 尝试或原生压缩完成后，保持期要求至少 4 轮真实工具工作，并积累 `max(5000字符, 15%)` 的历史增长。OCC 根据观察到的工作增长估计剩余复用次数，以普通输入∶输出∶缓存输入 = **1∶5∶0.1** 比较费用，同时要求候选留足容量余量。这组相对权重专用于 OCC 调度，实际金额以 provider 账单为准。

`compactionSummaryMaxTokens` 设置 Pi 普通文字压缩的输出上限，适用于手动、阈值、溢出和 OCC；0 沿用 Pi/模型限制。远端加密检查点由对应协议管理。`summaryBudget.nativeTargetTokens` 默认 16,384，是 OCC 的文字软目标；普通 Pi 压缩继续使用自己的提示与触发线。

发生截断、保护内容过多、源变化或预算不足时，OCC 保留原历史。

## 状态、性能与维护

- `pending` 表示视图仍使用原文，正在等待压力、费用、近期保护或有效摘要等条件。
- 摘要的输入、输出和失败请求用量单独统计。请求尚无 usage 时，费用预测继续采用预留值。
- 维护结束后，有效且尚未完成的 Goal 续推会恢复；新输入、暂停和取消状态在恢复前复核。
- 编辑来源、切换分支、修改保护配置或模型后，Condense 会重新校验旧摘要与费用判断。只有归档与当前来源同时有效，替换才能发布。
- 自动候选读取活动投影；完整分支统计缓存字符数、语义边界、工具 ID 和保护路径。首次读取分段让出，追加消息只读取新来源；保护规则和 frontier 变化沿用原分支口径重新计算。
- 同一同步工作片复用 Native 用量，跨 `await` 或来源、模型、Native 状态变化后重新读取。SDK 的 16 MiB 热正文缓存用于控制读取内存，历史可见性由投影决定，模型上下文上限由模型与 Pi 设置决定。实现见 [SDK 补丁说明](../../sdk-patches/pi-1.5.2/README.md)。
- 算法与状态机的验证范围见 [TLA+ 模型说明](../../test/formal/README.md)；性能与费用结论另需运行证据。

OpenAI/Codex 的加密检查点、OAuth 和跨模型迁移见[远端压缩](codex-compaction.md)。来源与许可见 [NOTICE](../../NOTICE) 和 [LICENSE](../provenance/condense/LICENSE)。
