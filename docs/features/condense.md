# Condense：历史整理与原文恢复

Condense 把较长的工具历史整理成摘要、去重引用或归档预览。模型在后续请求中读取整理后的视图。原始参数和结果保存在会话归档中，需要时可用 `context_tree_query` 查询。

模型摘要是有损视图，细节以原文为准。改写历史会改变请求前缀，因此实际收益取决于后续请求的数量与缓存复用情况。

**自动历史整理与空闲整段压缩（OCC）的初始状态均为关闭。**

## 启用与配置

```text
/pruner settings
/pruner on
/pruner status
```

配置位于全局的 `<agentDir>/metis-pi.toml` 中的 `[contextPrune]`。`agentDir` 默认为 `~/.pi/agent`，可用 `PI_CODING_AGENT_DIR` 覆盖。`/pruner` 命令直接保存设置。手动编辑文件后，执行 `/reload`。

| 命令 | 作用 |
| --- | --- |
| `/pruner settings` | 修改摘要模型、触发方式与保护项。 |
| `/pruner on`、`off` | 开关本地历史整理。归档查询始终可用。 |
| `/pruner status`、`stats` | 查看当前设置、整理进度与摘要用量。 |
| `/pruner now` | 在 Condense 已开启时，立即处理 pending。 |
| `/pruner compact` | 整理所有具备有效摘要的闭合小 chain，忽略 `rollingWindow`。 |
| `/pruner help` | 查看全部子命令。 |

字段、默认值与单位见[配置参考](../../metis-pi-config.md#contextprunecondense--occ)。

## 三层分组

消息边界决定分组方式。token 数量用于之后的收益与费用评估。

| 单位 | 范围 |
| --- | --- |
| 小 batch | 一次主模型请求产生的工具调用及其结果。同一请求中的多个工具调用组成一批。 |
| 小 chain | 从一条完整可见的 assistant 文本回复开始，到下一条文本回复、用户输入或 Goal 续推之前。 |
| 大 chain | 从一次用户输入或 Goal 续推开始，到下一次用户输入或 Goal 续推之前。 |

例如：用户提出任务，assistant 回复 A，然后两轮工具调用，接着 assistant 回复 B，再一轮工具调用，最后用户再次输入。这段历史包含三个小 batch、两个小 chain 和一个大 chain。

文本边界来自完整消息中的非空 `text`，包括同时含文本与工具调用的消息。thinking、流式片段、工具输出和 Condense 派生的消息，归属于所在的段。用户输入到第一条 assistant 文本之间的工具工作，形成独立的起始段。每个新边界开启下一段。

下一个边界出现之前，当前段保持开放。大任务中已闭合的段可以独立进入候选评估。“闭合”表示文本范围已经完整。随后一次成功的主模型响应确认其中的工具结果已被消费。失败、中断或被截断的响应，原文继续保留。

`batchingMode="turn"` 保持请求批次相互独立。`"agent-message"` 把同一小 chain 中相邻的批次合并。单次摘要最多包含 24 个工具调用，超出输入预算时拆分为多个 chunk。语义边界在各 chunk 之间保持一致。

## 何时整理

`pruneOn="agent-message"` 在完整可见的文本回复之后评估，是默认模式。`"on-demand"` 同时支持手动的 `/pruner now`，以及在工具轮次上根据压力、增长或尾部积压触发。每次触发都要经过下文的保护、收益和预算检查，然后才决定是否替换。

| 处理方式 | 生成方式 | 适用条件与结果 |
| --- | --- | --- |
| 精确去重 | 本地哈希 | 工具名与结果正文完全相同，且已有可恢复的记录。每次执行保留独立的参数、状态与引用。 |
| 规则摘录（packing） | 本地规则 | 处理可识别的成功构建、测试等输出。保留首尾，以及错误、警告与结果行。 |
| 工具结果摘要 | 摘要模型 | 归档完整、已被消费，且位于近期保护范围之外的旧结果。通过收益、预算与费用检查后生成摘要。 |
| 小 chain 整理 | 复用已有摘要 | 把闭合段的工具历史替换为已有摘要与恢复引用，保留边界文本。 |
| 大输出落盘（spill） | 本地归档 | 单个结果超过 `spillThreshold` 时保存原文，视图中留下预览与引用。默认门槛为 65,536 字符。 |

自动摘要、packing 与 chain 整理都要求结果已被模型消费，并应用共同的近期保护。spill 在捕获阶段按大结果规则生成预览与引用。“已归档”与“模型已消费完整结果”是两个独立的状态。失败调用的参数与图片数量由各自的设置管理。

### 付费摘要压力与预算

设模型窗口为 `W`，Pi 自动压缩的有效容量为 `T = W − reserveTokens`。付费摘要的默认压力线为：

```text
min(autoBudgetThreshold × W, maxBudgetWindowTokens, max(0, T − growthHeadroomTokens))
```

默认的 `autoBudgetThreshold` 为 0.7，`maxBudgetWindowTokens` 为 300,000，`growthHeadroomTokens` 为 16,384。`T` 有解析结果时才参与计算。自动付费摘要还要求上下文用量有效。`summaryBudget.maxBudgetWindowTokens` 只配置付费压力线的上限，与近期原文保护量无关。

`autoBudgetThreshold=false` 只关闭自动付费摘要。手动整理、本地规则与 Pi 原生压缩仍使用各自的入口。增长与尾部积压触发，同样需要通过付费压力和收益检查。

剩余待摘要内容少于 `minBatchChars`（默认 5,000 字符）时保留原文。设为 0 后，各批次直接进入后续的预算检查。

默认的单次付费替换，至少要净省 `max(2048, 被替换结果的 40%)` 个本地计数 token。完整的摘要消息最多 6,144 个 token，恢复引用、预览与包装都计入。单次摘要的工具历史输入上限为 65,536 字符。小窗口模型会进一步收紧该上限。

软目标会收缩到硬预算以内，但仍须容纳必要包装和至少 256 token 的正文空间。无法同时满足时保留原文。摘要为空、截断或替换后变大时，同样保留原文，pending 等待后续处理。本地计数采用归一化消息的 o200k 分词。预算公式见[摘要预算参数](../../metis-pi-config.md#contextprunesummarybudget摘要预算)。

摘要请求用完整消息额度的两倍作为文本 token 余量，至少 1,024。思考模型再按档位预留：minimal 为 1,024，low 为 2,048，medium/default 为 8,192，high/xhigh 为 16,384。这只分配响应空间，不改变请求的思考档位；关闭思考或不支持思考的模型不加这一项。总上限还受模型能力与原有窗口四分之一的限制。请求和费用预留使用同一上限，原生适配器追加的思考也须包含在内。这是输出余量策略，不是 provider 与 o200k 的固定换算；最终仍检查完整摘要，实际费用按 usage 结算。

### 近期原文与 chain 选择

自动工具摘要与 chain 整理共同保护以下内容，取各项的并集：

- 最近 **32,768 个估算 token** 的原文尾部（`minRecentTokens`）。
- 最近 **4 轮有效工具工作**（`minWorkTurns`）。有效轮次要求主请求成功，且工具结果有效。
- 等待模型消费的结果、指定保护的工具与路径，以及回读宽限期内的内容。
- 开放的小 chain 的完整原文。

默认的 `rollingWindow=3` 最多参考三个近期闭合的小 chain。它与开放组共用 `minRecentTokens` 预算。选择从近到远进行，以完整的组为单位。下一组超出预算时，选择结束。近期尾部与有效工作保护各自独立生效。

`rollingWindow=0` 关闭链数参考，其余保护保持不变。显式设置 `minRecentTokens=0` 会取消原文最低量与引用组的 token 限额。工作轮次及其他保护仍然生效。

手动的 `now` 使用配置的引用窗口。`compact` 覆盖全部安全的闭合组。两者都保留指定的保护，并要求归档完整、实际缩小。

## 缓存与费用

自动工具摘要、packing 与 chain 整理共用累计费用状态与再次改写的条件。

1. **局部收益。** 闭合、已被消费、正文为 2,048 至 65,536 个估算 token 的独立请求片段或小 chain，按自身收益评估。该区间用于选择经济计算档位。小 chain 始终按消息边界定义。自动 chain 维护先尝试最新三个有界候选，再尝试至多一个较旧候选：按估算体积选最大者，相同时选修改点更晚者。每个候选都要通过实际收益与费用检查。独立候选都失败后，仍保留共享组的评估。更大的候选与共享组按整体收益评估。
2. **总成本预测。** 总输入取本地投影与 Pi 当前用量估计中较大的值。净收益取两种本地计数中较小的值。改写后的第一个冷请求单独计费。之后两条路径每次请求新增 2,000 token，目标缓存命中率为 98%，缓存量受上一次请求长度的约束。每次请求按各自的输入量选择报价阶梯。压缩侧（含摘要费用）必须严格更便宜。
3. **预测范围。** 普通 batch 的聚合比较后续 3 次请求。自动大 chain 与共享的机械整理比较 24 次。有界的独立候选最多比较 32 次。这个数值描述费用预测的范围，实际整理发生在当前检查点。摘要请求发起前，按输入与输出上限预留费用。尚未收到 usage 的请求沿用预留值。
4. **发布后复核。** 首个请求的回执，按输入、缓存读取与写入用量校正冷请求的增量费用。超出预测的损失计入待偿余额。用量缺失时保留全冷重建的预留。后续改写要求余额结清，并新增至少 `max(minGainTokens, 上次净收益 / 4)` 的有效工作 token。对有缓存折扣的模型，还要求冷请求之后连续 3 次主请求成功，且每次实际缓存命中率至少 90%。

普通历史按内容不变的模型消息前缀估计首轮复用。旧压缩块重新渲染后仍可计入。远端检查点使用最近一次已观测请求及其缓存回执。会话、模型路由、检查点、来源编辑、提示词与工具定义都一致时，从实测缓存量中扣除整个受影响后缀的估算量，剩余部分计入首轮缓存。当前投影在上次请求之后已有变化时，按更早的变化位置扣除。缺少匹配证据时采用全冷预算。Pi 用量未知时，等待有效回执。

请求依据只借用最近一次模型输入的消息引用。发布或重置时释放。Pi 用量取自最近的 provider 回执，并结合之后的消息推算。这涵盖本地投影之外的请求开销。改写后的第一个回执会继续校正预测与实际缓存的差额。

有界候选的绝对收益底线为 `min(2048, chainCompression.minGainTokens)`，比例按候选自身计算。较大的 chain 候选与共享 chain 组，使用默认的 8,192 和总上下文 10% 的门槛。工具摘要先逐一满足局部摘要预算，再纳入共享的费用状态。

上下文超过 **256,000** 个估算 token 后，有界独立候选的修改范围限定在最后 **192,000** token 以内的旧内容。近期保护规则保持不变。这两个数值用于候选筛选。模型窗口与压缩目标由各自的设置决定。

预测基于固定的增长与缓存条件。实际费用以 provider 的 usage 与账单为准。短任务可能在冷请求和摘要费用摊回之前就结束了。无缓存折扣的模型，应把费用与工作增长作为复核条件。

### 报价来源与刷新

报价按以下顺序解析：

1. Pi 已注册模型的价格与上下文阶梯。先精确匹配，再用受限的正则匹配分隔符和日期别名。`mini`、`pro`、`flash` 等型号限定词参与匹配。同一模型的多个报价一致时，才采用。
2. [models.dev](https://models.dev/) 的本地快照，包括可识别的上下文阶梯价。
3. 前两项都没有报价时，使用**缓存输入 : 普通输入 = 1 : 10** 的相对成本估算。相对单位用于策略比较。账单金额以 provider 为准。

缓存位于 `<agentDir>/cache/metis-model-prices.json`。启动、切换模型和新的用户任务时，Condense 会检查 Pi 的 `models-store.json` 与 Metis 的安装标记。来源变化会触发目录重读。需要时在后台查询 models.dev。已有快照继续提供报价。首次查询期间，自动改写等待结果。

`pi update --models` 对模型目录的修改，会在下一次检查时生效。Metis 安装或更新时的 `postinstall` 会写入刷新标记。`pi update --extensions` 更新 Metis 后也会生效。其他时间沿用当前快照。查询失败时，保留已有报价或回退到相对估算。同一来源版本只尝试一次。

## 临近 Pi 原生压缩时

Pi 自动压缩已启用，且有效容量 `T` 可解析时，上下文达到 **90% × T** 之后，新增的改写交由 Pi 原生压缩接管。当前前缀保持稳定，Goal 继续运行。Pi 在自然增长达到容量线时执行压缩。

这个交接涵盖 pending 摘要、去重、参数整理、spill、chain 以及主动的 OCC。在途的候选进入该区间后，发布阶段会保留原文。已发生的摘要费用照常入账。已发布的整理结果继续重验与恢复。手动的 `now` 与 `compact` 仍然可用。

## 摘要模型与故障处理

`summarizerModel="default"` 跟随当前会话模型。也可指定已注册的 `provider/model-id`。故障切换按以下顺序尝试：主摘要模型、`summarizerFallbackModels`、当前会话模型。重复项以首次出现的位置为准。

摘要模型与备用模型会接收该批工具的参数和结果。跨 provider 配置时，应选择资料权限允许的模型。

认证失败、模型不可用、超时和 provider 故障，都会使用备用链。空输出、截断或预算拒绝，会结束当前候选并保留原文。成功的备用模型会被复用。10 分钟后可重试主摘要模型。

## 原文与分页恢复

归档位于会话旁的 `<sessionId>-blobs/`。备份、移动或清理会话时，需一并处理。归档在显示截断之前捕获输出，并导入 Pi bash 的完整输出文件。可恢复范围以 `archiveComplete` 为准。上游缺失时会明确标记。

`context_tree_query` 是延迟加载的工具。通过 `tool_search` 获取参数后，可直接调用，也可在 codemode 中使用。省略选择器时先列出证据目录，取得引用后再读取内容：

| 参数 | 用法 |
| --- | --- |
| `toolCallIds` | 工具原始 ID、`t12` 之类的短引用，或 `b1` 之类的 chain 块引用。重复的原始 ID 返回各次已索引的记录。 |
| `parentToolCallId` | 按父调用读取子调用的归档，包括 codemode 界面预览中省略的部分。 |
| `sourceEntryIds` | 读取当前分支上的历史消息、压缩或摘要条目。组件为 `output`。 |
| `component` | 默认 `output`。`arguments` 读取原始参数，支持 `toolCallIds` 或 `parentToolCallId`。 |
| `maxBytes` | 每页完整 JSON 的字节预算，包括元数据与游标。范围 2,048 至 32,768，默认 32,768。 |
| `cursor` | 使用上一页的 `nextCursor`。选择器与 `component` 必须保持一致。 |

`toolCallIds`、`parentToolCallId`、`sourceEntryIds` 三者只能选其一。分页按 UTF-8 安全边界切分。游标校验会话、当前分支的可见性、选择条件与内容版本。来源失效后，从新的第一页开始。

`eof` 描述分页进度。`archiveComplete` 描述原始捕获的完整性。归档缺失、未结束或捕获不完整，都会返回明确的状态。查询结果反映归档时的内容。当前文件或运行中进程的状态，需要另行获取。

原文回读会开启 `recoveryGraceTurns` 保护，默认持续 3 个大任务边界。用户输入或 Goal 续推各计一次。

## 空闲整段压缩（OCC）

OCC 使用 Pi 的普通文字摘要。它由 `enabled` 与 `opportunisticCompaction` 共同开启。它在回复结束、消息已交付且工具空闲时尝试。远端加密路径拥有请求时，由远端路径完成压缩。

Pi 自动压缩启用后，OCC 按有效容量 `T` 调度：达到 60% 开始等待，达到 72% 可以就绪，低于 52% 退出等待，达到 90% 时交给自然压缩。等待三轮工作后仍未就绪，本地摘要可以恢复执行。每次用户或 Goal 请求最多尝试一次 OCC。

本地改写发布、OCC 尝试或原生压缩完成后，保持期要求至少 4 轮真实的工具工作，并累积 `max(5000 字符, 15%)` 的历史增长。OCC 根据观察到的工作增长估计剩余的复用次数。它以普通输入 : 输出 : 缓存输入 = **1 : 5 : 0.1** 比较费用。同时要求候选留有足够的容量余量。这组相对权重只用于 OCC 调度。实际金额以 provider 账单为准。

`compactionSummaryMaxTokens` 设置 Pi 普通文字压缩的输出上限。适用于手动压缩、阈值压缩、溢出压缩和 OCC。设为 0 时沿用 Pi 与模型的限制。远端加密检查点由对应的协议管理。`summaryBudget.nativeTargetTokens` 默认为 16,384，是 OCC 的文字软目标。普通 Pi 压缩仍使用自己的提示与触发线。

发生截断、保护内容过多、来源变化或预算不足时，OCC 保留原历史。

## 状态、性能与维护

- `pending` 表示视图仍使用原文，正在等待压力、费用、近期保护或有效摘要等条件。
- 新写入与重建的归档使用相同的轻量目录。完整参数与结果只在当前 Native 活动窗口中缓存。历史回读不常驻正文。自动压缩、手动 `/compact` 或 OCC 成功后，旧窗口的整理任务停止，其缓存和排队正文随之释放。仍有效的工作从持久来源恢复。失败或取消不会丢弃原队列。
- 压缩不删除归档目录，也不等于清空进程或立即降低 RSS。历史条数增长仍会带来元数据与查询成本。
- 摘要的输入、输出与失败请求用量单独统计。请求尚无 usage 时，费用预测沿用预留值。
- Goal 续推在维护结束后恢复，前提是它仍有效且尚未完成。新输入、暂停与取消的状态在恢复前复核。
- 编辑来源、切换分支、修改保护配置或模型之后，Condense 会重新校验旧摘要与费用判断。只有归档与当前来源同时有效，替换才会发布。
- 自动候选读取活动投影。完整的分支统计缓存字符数、语义边界、工具 ID 与保护路径。首次读取时分段让出。追加的消息只读取新来源。保护规则与 frontier 变化时，按原分支口径重新计算。
- 同一同步工作片内复用 Native 用量。跨 `await`，或来源、模型、Native 状态变化之后，重新读取。SDK 的 16 MiB 热正文缓存用于控制读取内存。历史可见性由投影决定。模型上下文上限由模型与 Pi 设置决定。实现见 [SDK 补丁说明](../../sdk-patches/pi-1.5.2/README.md)。
- 算法与状态机的验证范围见 [TLA+ 模型说明](../../test/formal/README.md)。性能与费用的结论还需要运行证据。
