# 0.17.0 — 把 codex-conversion 纳入 pi-codexy（vendor 源码 + 仓库内构建）

状态：**已完成**（M0–M5，0.17.0）。上游：`@howaboua/pi-codex-conversion` 3.0.34（MIT）。
实测补充：dist 真实字节 1.8MB（11 个 `.d.ts` 仅联合成员顺序差异），vendored 树真实字节 11.7MB；
pty 需要给隔离 HOME 播种插件配置（`alt+u` 快捷键 + changelog suppress），否则上游默认
`alt+q` 与 pi 内置冲突并渲染 what's-new 块，都会打乱坐标型阶段。
本计划是这次改造的权威依据；实现中若发现新事实，改这里再改代码。

## 为什么

`@howaboua/pi-codex-conversion` 是本栈里唯一还在第三方 npm 包里的功能件，而它需要被本地修补
（已有一处：`notebook` 工具参数 schema 必须是顶层 object，否则 DeepSeek 直接 400），
而 `pi update` 会覆盖 npm 包 → 修补丢失。目标：**代码进 pi-codexy、patch 进 pi-codexy 的 git，
上游升级变成一次显式的、可验证的 resync**。

## 已核实的事实（决定架构，不是猜测）

1. 上游是 monorepo：`github.com/IgorWarzocha/howaboua-pi-stuff`，包目录
   `packages/pi-codex-conversion`；本地纯净副本在 `references/howaboua-pi-stuff/`（gitignore）。
   本次记录的上游版本 = 3.0.34。
2. **运行时资源按 `packageRoot()` 相对定位**（= 从 `dist/tools/native/binary.js` 上溯 4 层），
   所以 vendored 树必须保持内部结构：`dist/`、`vendor/`、`code-mode/`、
   `src/tools/<tool>/bin/<platform>-<arch>/`、`changelog.js`、`package.json`（运行时读它的 version）。
3. **构建可行且可复现**：`tsc -p tsconfig.build.json`（TS 5.9.3 + 上游 `tsconfig.base.json`，
   需去掉 bun 专有的 `stableTypeOrdering`）产出 321 个 `.js`；与 npm 发布版 dist 逐文件对比：
   仅 11 个 `.d.ts` 有声明格式差异，`.js` 只有我们故意改的那一个。**构建产物可信**。
4. **源码不能直接加载**：`src/**` 有 110 处 `from "./x.js"` 说明符（NodeNext 风格），
   Node 类型剥离不做 `.js`→`.ts` 重写 → 必须有构建步骤。所以采用「vendor 源码 + 仓库内构建」。
5. **pi 会给 git 装的扩展跑 `npm install` 并自动修复缺失依赖**
   （`installGit` → npm install；`hasMissingGitDependencies` → 自动补装），
   所以在 pi-codexy 的 `package.json` 里声明运行时依赖即可，不需要 vendor node_modules。
6. 载荷（用户已拍板：**仅 linux-x64，不含语音**）：`src/**/*.ts` 1.6MB + `dist/` 3.7MB +
   `vendor/` 3.6MB + `src/tools/{exec,apply-patch,view-image}/bin/linux-x64` 3.7MB + `code-mode/` 36K
   ≈ **12.7MB**（上游整包 73MB 里 43MB 是各平台语音二进制，全部剔除）。
7. 没有任何其它包 import 这个包的 subpath exports（只有 lock 文件提到它）→ 替换成 vendored 版本是封闭的。

## 目标布局

```
pi-codexy/
├── package.json                      pi.extensions: ["./extensions/*.ts", "./vendor/pi-codex-conversion/dist/index.js"]
│                                    dependencies: + openai partial-json proxy-from-env selfsigned smol-toml undici web-tree-sitter ws
│                                    files: + vendor ; scripts: + vendor:build / vendor:check / vendor:patch / vendor:sync
├── vendor/pi-codex-conversion/
│   ├── src/**                        # 321 个上游 .ts（我们的 patch 直接落在这里）
│   │   └── tools/{exec,apply-patch,view-image}/bin/linux-x64/**   # 3.7MB 原生工具
│   ├── vendor/**                     # tree-sitter-bash.wasm + js-tiktoken ranks
│   ├── code-mode/**                  # code-mode host 资产/notices
│   ├── types/**                      # 公开类型声明
│   ├── changelog.ts + changelog.js   # 运行时动态 import（源码态走 .ts、构建态走 .js）
│   ├── dist/**                       # 构建产物，提交（pi 直接加载，安装期零构建）
│   ├── tsconfig.json|tsconfig.build.json|tsconfig.base.json   # 上游为基础，去掉 bun 专有选项
│   ├── package.json                  # 裁剪版：name/version/type/deps/peerDeps（运行时读 version）
│   ├── LICENSE                       # 上游 MIT
│   ├── UPSTREAM.md                   # 出处：repo / npm 版本 / commit / resync 步骤
│   ├── PATCHES.md                    # 我们的 patch 清单与理由
│   └── patches/local.patch           # 相对上游源码的合并 patch（resync 时重放）
├── scripts/vendor-codex-conversion.mjs   # build / check / save-patch / sync 四个动作
└── references/howaboua-pi-stuff/**    # 纯净上游源码（gitignore，只读参考）
```

要点：
- **发布态加载 `vendor/.../dist/index.js`**（`.js`），与上游 npm 包同形；dist 进 git，安装期不构建。
- **patch 打在 `src/**`**，然后 `vendor:build` 重建 dist：patch 是源码级的，可读、可 review。
- vendored 目录有自己的 `package.json`（运行时读 version）+ 自己的 tsconfig，
  与 pi-codexy 自身的 `tsconfig.json`（仓库 tsc 检查）互不干扰：**仓库 tsc 排除 `vendor/`**。

## 里程碑（顺序即依赖顺序）

- **M1 树落位**：建 `vendor/pi-codex-conversion/`；从 `references/` 拷 `src`（剔除语音二进制、
  只留 linux-x64 原生工具）、`vendor`、`code-mode`、`types`、`changelog.ts`、LICENSE、
  裁剪版 package.json、三份 tsconfig（去 `stableTypeOrdering`）；写 `UPSTREAM.md`。
  验收：`du -sh vendor/` ≈ 5.3MB（dist 未建）；文件数与上游 src 一致。
- **M2 构建链**：`scripts/vendor-codex-conversion.mjs` 的 `build` 动作（tsc → dist + changelog.js），
  `check` 动作（vendored tsconfig 类型检查）。验收：构建产物与 npm 发布版 dist 的差异 ≤ 已知 11 个 `.d.ts`；
  `npm run vendor:check` 0 error。
- **M3 集成**：manifest 加 vendored 入口；`dependencies` 加 8 个运行时依赖并本地 `npm install`；
  `files` 加 `vendor`；把已有的 notebook patch 落到 vendored **源码**（不是 dist）；
  用 `/tmp/ext-resolve.mjs` 验证解析结果。
  验收：解析器显示 vendored 入口 ON；仓库自身 tsc/测试不受影响。
- **M4 验证**：vendored 加载冒烟（真实 fake-pi 激活，断言注册的工具名集合）；
  `npm test` 368 全绿；`check`/`check:core` 0 error；`host-smoke`；`test:pty` rc=0；
  `npm pack --dry-run` 含 vendor。验收：全部通过。
- **M5 收口**：README 新章节（vendored 说明 + 升级流程）、CHANGELOG 0.17.0、VALIDATION 条目、
  版本号 0.17.0；提交（不推送）。用户确认后：settings 禁用 npm 包 → push → `pi update --extensions`
  → 重启验证 codex 工具仍在。

## 补丁与升级流程（长期）

- 每个 patch 在 `PATCHES.md` 记：文件、现象、根因、改法、验证方式。
- `npm run vendor:patch`：把 `vendor/**` 与 `references/` 上游的差异导出成 `patches/local.patch`。
- 升级：更新 `references/` 上游 → `npm run vendor:sync`（拷贝新源码 → 重放 `patches/local.patch`
  → 构建 → 报告冲突）→ 跑 M4 全套 gate → 提交。
- 已知 patch 清单（当前 1 条）：`notebook` 工具参数 schema 顶层必须是 object
  （DeepSeek 等严格 provider 会 400 拒绝整个请求）。

## 未决 / 风险

- `changelog.js` 由上游 monorepo 脚本生成；若该脚本不能独立运行，则回退为「拷贝 npm 发布版
  changelog.js」并在 PATCHES.md 记明。**未知，M2 验证。**
- vendored 树里 `package.json` 的 `name` 仍是 `@howaboua/pi-codex-conversion`（运行时做版本比较用），
  不等同于「我们发布了这个包」——LICENSE/UPSTREAM.md 会写清来源；`NOTICE` 里加一条归属声明。
- 上游迭代快（本包频繁发版）：pin 在 3.0.34，升级是显式动作，不自动跟随。
- 语音/跨平台功能在 vendored 版本中不可用（用户已确认不需要）；`src/voice/bin` 缺失时
  只在使用时失败，不影响加载。
